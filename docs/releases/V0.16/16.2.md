# BC-16.2 — Instrumentation de l'application

# Objectif

Cette sous-issue instrumente les principales fonctionnalités de BadCalendar afin d'enregistrer les métriques d'utilisation définies dans la BC-16.1.

L'objectif est de mesurer les usages réels de l'application pendant la phase pilote sans impacter l'expérience utilisateur.

---

# Contexte

Le modèle de collecte est désormais disponible.

Cette sous-issue consiste à déclencher les événements appropriés lors des interactions de l'utilisateur.

Chaque action importante doit produire un événement unique.

---

# Principes

L'instrumentation respecte les principes suivants :

- un événement correspond à une action utilisateur ;
- aucun événement n'est enregistré automatiquement sans raison fonctionnelle ;
- aucune donnée personnelle n'est collectée ;
- les événements sont indépendants les uns des autres ;
- le tracking ne doit jamais ralentir l'application.

---

# Événements instrumentés

Les événements suivants sont enregistrés.

## Ouverture de l'application

EventType

```text
app_open
```

Déclenché à chaque nouvelle session.

---

## Modification d'un filtre

EventType

```text
filter_changed
```

EventCategory

- Category
- Type
- Scope
- RegistrationState
- Month

EventValue

Valeur sélectionnée ou désélectionnée.

Un événement est enregistré pour chaque modification.

# Granularité

Chaque action utilisateur produit un seul événement.

Exemple :

- ouverture d'une carte → 1 événement ;
- clic BadNet → 1 événement ;
- clic Google Maps → 1 événement.

Aucun doublon ne doit être enregistré.

---

# Ordre des événements

Les événements sont enregistrés immédiatement après l'action utilisateur.

Le tracking ne bloque jamais l'exécution de l'action.

---

# Gestion des erreurs

En cas d'échec :

- aucune erreur n'est affichée ;
- l'action utilisateur est tout de même réalisée ;
- l'échec du tracking est ignoré.

Les métriques ne doivent jamais dégrader l'expérience utilisateur.

---

# Performance

L'instrumentation doit avoir un impact imperceptible sur le temps de réponse.

Le nombre d'événements générés reste faible.

Aucune optimisation spécifique n'est nécessaire.

---

# Architecture

Les composants de l'application ne construisent jamais eux-mêmes les événements.

Ils appellent uniquement :

```text
UsageMetricService.track(...)
```

Le service est responsable :

- de la création du modèle ;
- de l'ajout des informations de contexte ;
- de l'appel au backend.

---

# Évolutivité

L'ajout d'un nouvel événement doit uniquement nécessiter :

- un nouvel EventType ;
- un appel supplémentaire au UsageMetricService.

Aucune modification de l'architecture existante ne doit être nécessaire.

---

# Hors périmètre

Cette sous-issue ne comprend pas :

- tableau de bord Google Sheets ;
- graphiques ;
- analyse statistique ;
- recommandations automatiques.

Ces sujets seront traités dans la BC-16.3.

---

# Critères d'acceptation

La sous-issue est considérée terminée lorsque :

- toutes les actions principales sont instrumentées ;
- aucun doublon n'est enregistré ;
- le tracking n'impacte pas les performances ;
- une erreur de collecte n'interrompt jamais l'application ;
- tous les événements utilisent UsageMetricService.
