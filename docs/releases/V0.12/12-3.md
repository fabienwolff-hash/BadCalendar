# BC-12.3 — Refonte de ValidationService

## Version

v0.12

---

# Contexte

Le modèle métier de BadCalendar repose désormais sur les entités :

- Tournament
- Program
- Site

ValidationService doit évoluer afin de valider ce nouveau modèle.

Cette évolution ne modifie pas le principe général :

la validation est réalisée exclusivement dans la partie Administration.

Le frontend ne réalise aucune validation.

TournamentService considère toujours que les données sont valides.

---

# Objectif

Faire évoluer ValidationService afin de :

- conserver toutes les validations existantes ;
- intégrer les nouvelles règles liées au modèle Tournament ;
- produire des rapports d'erreurs plus cohérents.

# Principes

ValidationService reste le seul responsable de la qualité des données.

Il est exécuté avant toute utilisation du Master.

TournamentService ne valide jamais les données.

Le frontend ne valide jamais les données.

---

# Niveaux de validation

Les règles sont désormais organisées selon trois niveaux.

## Niveau Tournament

Validation des propriétés communes.

Exemples :

- TournamentId obligatoire
- unicité du TournamentId
- titre obligatoire
- type obligatoire
- portée obligatoire
- organisateur obligatoire
- URL valide
- dates d'inscription cohérentes

Toutes les lignes d'un même Tournament doivent partager les mêmes propriétés.

---

## Niveau Program

Validation des informations spécifiques au programme.

Exemples :

- discipline
- catégories
- date
- mode de participation

Chaque ligne représente un Program.

---

## Niveau Site

Validation du lieu.

Exemples :

- ville obligatoire
- gymnase optionnel

---

# Validations conservées

Toutes les validations existantes restent applicables lorsqu'elles sont toujours pertinentes.

Le changement concerne uniquement leur organisation.

---

# Nouvelles validations

Ajout des règles suivantes :

## Cohérence d'un Tournament

Toutes les lignes d'un même Tournament doivent posséder les mêmes valeurs pour les propriétés communes.

Exemples :

- titre
- type
- portée
- inscription
- URL

Toute différence constitue une erreur.

---

## Détection des Tournament incomplets

Un Tournament sans Program valide est signalé.

---

## Validation des Sites

Les informations de localisation doivent être cohérentes.

---

# Rapport de validation

Le rapport continue de fonctionner comme aujourd'hui.

Les erreurs sont simplement regroupées de manière plus logique.

Exemple :

Tournament T025

- titre incohérent
- URL différente
- portée différente

Program du 12/10

- catégorie invalide

Site

- ville manquante

---

# Impact Backend

ValidationService évolue.

TournamentService ne change pas.

---

# Impact Frontend

Aucun.

---

# Compatibilité

Le fonctionnement de la partie Administration reste identique.

L'utilisateur ne constate aucun changement.

---

# Tests

Les tests doivent vérifier notamment :

- cohérence d'un Tournament ;
- propriétés communes identiques ;
- Program invalide ;
- Site invalide ;
- rapport produit correctement.

Chaque nouvelle règle métier doit être accompagnée d'un test.

---

# Hors périmètre

Cette sous-issue ne comprend pas :

- migration du frontend ;
- optimisation des performances ;
- analytics.

---

# Critères d'acceptation

- ValidationService comprend le modèle Tournament.
- Toutes les validations existantes sont conservées.
- Les nouvelles règles sont implémentées.
- Le rapport reste compatible avec l'administration.
- Les tests sont passants.
- La documentation est mise à jour.
