# BC-1.4 — Préparation de la publication

# Objectif

Cette sous-issue prépare la publication officielle de BadCalendar v1.0.

Elle consiste à vérifier que l'ensemble du projet est prêt à être livré, tant sur le plan technique que documentaire.

Aucune nouvelle fonctionnalité n'est développée.

---

# Contexte

Les fonctionnalités sont développées.

Les retours de la campagne pilote ont été intégrés.

Le produit est désormais considéré comme stable.

Cette sous-issue consiste à effectuer les dernières vérifications avant la publication officielle.

---

# Vérification de la documentation

Vérifier que tous les documents du projet sont à jour.

## Produit

- vision.md
- philosophy.md
- product_principles.md

## Métier

- domain_model.md
- data_model.md
- business_rules.md
- glossary.md

## Architecture

- architecture.md
- coding_guidelines.md
- tests.md

## Fonctionnalités

- google_calendar.md
- filters.md
- usage_metrics.md
- navigation.md
- ux.md

## Gestion du projet

- roadmap.md
- backlog.md
- decisions.md
- release_note.md
- release_checklist.md

Le README principal doit refléter fidèlement la version publiée.

---

# Vérification technique

Contrôler notamment :

- aucune erreur JavaScript ;
- aucun avertissement bloquant ;
- aucun lien invalide ;
- aucun fichier obsolète ;
- aucune dépendance inutile.

---

# Vérification fonctionnelle

Contrôler que :

- les filtres fonctionnent ;
- Google Calendar fonctionne ;
- Google Maps fonctionne ;
- BadNet fonctionne ;
- les nouveautés sont correctement affichées ;
- les Usage Metrics sont opérationnelles.

---

# Vérification des données

Contrôler :

- le Master ;
- les catégories ;
- les liens BadNet ;
- les coordonnées des lieux ;
- les dates.

Les données de démonstration éventuelles doivent être supprimées.

---

# Vérification de la configuration

Contrôler notamment :

- numéro de version ;
- constantes de configuration ;
- URL du backend ;
- paramètres Apps Script ;
- paramètres Google Sheets.

---

# Release Notes

Finaliser :

- release_note.md ;
- changelog ;
- numéro de version.

La Release Note doit résumer les principales évolutions de la v1.0.

---

# Release Checklist

Valider l'ensemble de la Release Checklist.

Aucun élément ne doit rester non validé.

---

# Documentation utilisateur

Vérifier que l'utilisateur dispose des informations nécessaires pour comprendre :

- le rôle de BadCalendar ;
- son positionnement par rapport à BadNet ;
- les principales fonctionnalités disponibles.

---

# Hors périmètre

Cette sous-issue ne comprend pas :

- corrections fonctionnelles ;
- nouvelles fonctionnalités ;
- optimisation des performances.

Toute anomalie découverte est corrigée avant de poursuivre la publication.

---

# Critères d'acceptation

La sous-issue est considérée terminée lorsque :

- toute la documentation est synchronisée ;
- la Release Checklist est entièrement validée ;
- les Release Notes sont finalisées ;
- le numéro de version est définitif ;
- aucune anomalie bloquante n'est identifiée ;
- le produit est prêt à être publié.

---

# Livrable attendu

À l'issue de cette sous-issue :

- BadCalendar est prêt à être publié ;
- la documentation est complète ;
- la configuration est validée ;
- la publication officielle peut être réalisée dans la BC-1.5.
