# BC-16.1 — Modèle de collecte des métriques

# Objectif

Cette sous-issue définit le modèle de collecte des métriques d'utilisation de BadCalendar.

Elle introduit un service unique responsable de l'enregistrement des événements fonctionnels de l'application.

L'objectif est de disposer d'un format de données stable, simple et extensible avant d'instrumenter les différentes fonctionnalités.

---

# Contexte

BadCalendar doit permettre de mesurer l'utilisation réelle de l'application pendant la phase pilote.

Les métriques servent exclusivement à améliorer le produit.

Aucune donnée personnelle n'est collectée.

---

# Principes

Le système de collecte respecte les principes suivants :

- anonymat complet ;
- aucun compte utilisateur ;
- aucune donnée personnelle ;
- faible impact sur les performances ;
- format unique pour tous les événements ;
- architecture facilement extensible.

---

# UsageMetricService

La collecte des métriques est centralisée dans un service unique :

```text
UsageMetricService
```

Ce service constitue l'unique point d'entrée pour enregistrer un événement.

Aucun composant de l'application ne communique directement avec le backend.

---

# Format d'un événement

Chaque événement possède la structure suivante.

| Champ | Description |
|--------|-------------|
| Timestamp | Date et heure de l'événement |
| AppVersion | Version de BadCalendar |
| EventType | Type d'événement |
| EventValue | Valeur éventuelle associée |
| SessionId | Identifiant anonyme de session |

Le format est identique pour tous les événements.

---

# Session

Une SessionId est générée automatiquement lors de l'ouverture de l'application.

Elle permet uniquement de regrouper les événements d'une même visite.

Elle ne permet pas d'identifier un utilisateur.

Une nouvelle SessionId est créée à chaque nouvelle session.

---

# Version

Chaque événement contient la version de l'application.

Exemple :

```text
v1.0.0
```

Cette information permettra d'analyser les usages après chaque publication.

---

# EventType

Les événements sont identifiés par une valeur normalisée.

Exemples :

- app_open
- filter_changed
- tournament_opened
- badnet_open
- maps_open
- calendar_export

La liste pourra évoluer dans les versions futures.

---

# EventValue

Certains événements possèdent une valeur complémentaire.

Exemples :

```text
Category

Cadet
```

```text
Type

TRJ
```

```text
Scope

Regional
```

Lorsque l'événement ne nécessite aucune valeur, ce champ reste vide.

---

# Backend

Le backend reçoit un événement unique à chaque appel.

Il est responsable :

- de la validation ;
- de l'enregistrement dans Google Sheets ;
- de la gestion des erreurs.

Le frontend n'effectue aucun traitement métier.

---

# Robustesse

Une erreur d'enregistrement ne doit jamais empêcher l'utilisation de BadCalendar.

Les métriques sont considérées comme non bloquantes.

En cas d'échec :

- aucune erreur n'est affichée ;
- l'utilisateur poursuit normalement sa navigation.

---

# Performance

L'enregistrement des métriques doit être transparent.

Le temps de réponse de l'application ne doit pas être dégradé.

---

# Évolutivité

Le modèle doit permettre l'ajout futur de nouveaux EventType sans modifier le format des données.

Le schéma de stockage reste stable.

---

# Hors périmètre

Cette sous-issue ne comprend pas :

- instrumentation des fonctionnalités ;
- tableau de bord ;
- graphiques ;
- analyse statistique.

Ces sujets seront traités dans les sous-issues suivantes.

---

# Critères d'acceptation

La sous-issue est considérée terminée lorsque :

- UsageMetricService est créé ;
- le format des événements est unique ;
- SessionId est générée automatiquement ;
- AppVersion est renseignée ;
- le backend accepte ce nouveau format ;
- une erreur de tracking n'impacte jamais l'utilisateur.
