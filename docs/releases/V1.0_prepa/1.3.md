# BC-1.3 — Corrections issues du pilote

# Objectif

Cette sous-issue met en œuvre les corrections identifiées lors de la campagne pilote.

L'objectif est d'améliorer la qualité, la stabilité et l'expérience utilisateur de BadCalendar avant sa publication officielle.

Aucune nouvelle fonctionnalité n'est développée.

---

# Contexte

La campagne pilote a permis de recueillir :

- les retours des parents ;
- les observations du développeur ;
- les Usage Metrics ;
- les anomalies détectées.

Cette sous-issue consiste à appliquer uniquement les corrections nécessaires à la publication de la version 1.0.

---

# Principes

Les corrections respectent les principes suivants :

- priorité aux anomalies bloquantes ;
- amélioration de l'expérience utilisateur ;
- aucun changement majeur d'architecture ;
- aucune évolution fonctionnelle hors périmètre.

Les suggestions importantes mais non indispensables sont reportées après la v1.0.

---

# Catégories de corrections

Les corrections peuvent concerner :

## Bugs

Exemples :

- comportement incorrect ;
- erreur JavaScript ;
- mauvais affichage ;
- lien invalide.

---

## UX

Exemples :

- texte peu clair ;
- libellé ambigu ;
- manque de visibilité d'une information ;
- amélioration d'un message.

Les modifications restent limitées.

---

## Performance

Corrections simples lorsque celles-ci améliorent perceptiblement la fluidité de l'application.

Aucune optimisation lourde n'est entreprise.

---

## Données

Correction éventuelle :

- des informations du Master ;
- des liens BadNet ;
- des coordonnées Google Maps ;
- des catégories.

---

# Priorisation

Chaque anomalie est classée selon sa gravité.

## Bloquante

Empêche l'utilisation normale de l'application.

Correction obligatoire.

---

## Majeure

Dégrade fortement l'expérience utilisateur.

Correction recommandée.

---

## Mineure

Impact limité.

Correction si le délai le permet.

---

## Évolution

Suggestion ne correspondant pas au périmètre de la v1.0.

Ajout dans la roadmap des versions futures.

---

# Validation

Après chaque correction :

- vérifier le fonctionnement ;
- vérifier l'absence de régression ;
- mettre à jour la documentation si nécessaire.

---

# Documentation

Mettre à jour si nécessaire :

- release_note.md ;
- roadmap.md ;
- decisions.md ;
- release_checklist.md.

Les évolutions reportées sont ajoutées à la roadmap post-v1.0.

---

# Hors périmètre

Cette sous-issue ne comprend pas :

- nouvelles fonctionnalités ;
- refonte graphique ;
- évolution du modèle métier ;
- optimisation importante des performances.

Ces sujets seront étudiés après la publication.

---

# Critères d'acceptation

La sous-issue est considérée terminée lorsque :

- toutes les anomalies bloquantes sont corrigées ;
- les anomalies majeures retenues sont corrigées ;
- aucune régression n'est observée ;
- les évolutions reportées sont documentées ;
- la documentation est synchronisée.

---

# Livrable attendu

À l'issue de cette sous-issue :

- BadCalendar est stable ;
- les principaux retours du pilote ont été pris en compte ;
- les anomalies bloquantes ont disparu ;
- la version est prête pour la préparation de la publication.
