# BC-1.5 — Publication officielle

# Objectif

Cette sous-issue réalise la publication officielle de BadCalendar v1.0.

Elle consiste à déployer la version finale, vérifier son bon fonctionnement en environnement de production et clôturer le cycle de développement ayant conduit à la première version publique.

---

# Contexte

Toutes les fonctionnalités prévues pour la v1.0 sont terminées.

Les tests fonctionnels sont validés.

La campagne pilote est achevée.

Les corrections identifiées ont été intégrées.

Le produit est prêt à être mis à disposition des utilisateurs.

---

# Déploiement

Publier la version officielle de BadCalendar.

Le déploiement comprend notamment :

- création d'une nouvelle version Apps Script ;
- mise à jour du déploiement Web App ;
- vérification de l'URL publique ;
- vérification des autorisations d'accès.

L'URL publique devient la référence officielle de l'application.

---

# Vérification post-déploiement

Après publication, vérifier que :

- l'application est accessible ;
- les données sont correctement chargées ;
- les filtres fonctionnent ;
- Google Calendar fonctionne ;
- Google Maps fonctionne ;
- les liens BadNet sont valides ;
- les Usage Metrics continuent d'être enregistrées.

Ces vérifications sont réalisées directement sur l'environnement de production.

---

# Vérification des performances

Contrôler que :

- le temps de chargement reste conforme aux objectifs ;
- les interactions restent fluides ;
- aucune erreur JavaScript n'est observée ;
- aucun incident n'est détecté après publication.

---

# Communication

Préparer les éléments de communication liés à la publication.

Ils peuvent comprendre :

- annonce auprès des parents testeurs ;
- présentation au club ;
- mise à disposition de l'URL officielle ;
- diffusion de la Release Note v1.0.

La communication reste adaptée à l'échelle du projet.

---

# Versionning

Créer les éléments suivants :

- tag Git `v1.0.0` ;
- Release GitHub (si utilisée) ;
- archivage des documents de préparation.

La version 1.0 devient la nouvelle référence du projet.

---

# Clôture du projet de lancement

À la fin de cette sous-issue :

- clôturer toutes les issues de la roadmap v1.0 ;
- archiver la roadmap de lancement ;
- ouvrir la roadmap des versions futures.

Le backlog devient la source principale des évolutions à venir.

---

# Documentation

Finaliser les documents suivants :

- README.md ;
- release_note.md ;
- roadmap.md ;
- backlog.md ;
- decisions.md ;
- release_checklist.md.

La documentation reflète fidèlement la version publiée.

---

# Support

Préparer le suivi des premiers utilisateurs.

Les anomalies découvertes après publication sont enregistrées dans le backlog.

Les évolutions fonctionnelles sont étudiées pour les versions suivantes.

---

# Hors périmètre

Cette sous-issue ne comprend pas :

- nouvelles fonctionnalités ;
- évolutions UX ;
- refonte graphique ;
- changements d'architecture.

Toute évolution est reportée après la publication.

---

# Critères d'acceptation

La sous-issue est considérée terminée lorsque :

- BadCalendar v1.0 est publié ;
- l'application est accessible publiquement ;
- toutes les vérifications post-déploiement sont validées ;
- le tag `v1.0.0` est créé ;
- la documentation est finalisée ;
- la roadmap de lancement est clôturée.

---

# Livrable attendu

À l'issue de cette sous-issue :

- BadCalendar v1.0 est officiellement disponible ;
- les utilisateurs disposent d'une application stable, simple et documentée ;
- le projet entre dans une phase de maintenance et d'amélioration continue guidée par les retours utilisateurs et les Usage Metrics.
