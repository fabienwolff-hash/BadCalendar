# BC-13.4 — Initial Test Suite

## Objectif

Mettre en place la première suite de tests automatisés de BadCalendar.

Cette sous-issue inaugure l'utilisation de TestKit en couvrant les principaux services métier du backend.

L'objectif est de construire une première base de non-régression qui accompagnera les évolutions futures du projet.

---

# Contexte

Les sous-issues précédentes ont permis de mettre en place :

- TestKit ;
- les assertions ;
- les jeux de données de référence.

Cette sous-issue consiste à écrire les premiers tests métier afin de valider le bon fonctionnement des principaux services.

---

# Objectifs

À l'issue de cette sous-issue :

- les principaux services disposent d'une première couverture de tests ;
- les règles métier critiques sont vérifiées automatiquement ;
- la commande `runAllTests()` permet d'exécuter l'ensemble de la suite de tests.

---

# Hors périmètre

Cette sous-issue ne comprend pas :

- les tests du frontend ;
- les tests de performance ;
- les tests de charge ;
- les tests d'interface utilisateur.

Les validations visuelles continuent d'être réalisées manuellement avant chaque release.

---

# Services concernés

Les premiers tests concernent uniquement les services métier.

Ordre de priorité :

1. ValidationService
2. TournamentService
3. RegistrationService
4. ParameterService

Les services pourront être complétés progressivement lors des futures évolutions.

---

# Couverture attendue

## ValidationService

Les tests vérifient notamment :

- identifiant obligatoire ;
- unicité des identifiants ;
- type valide ;
- portée valide ;
- catégorie valide ;
- mode d'inscription valide ;
- cohérence des dates d'inscription.

Chaque règle métier importante doit disposer d'au moins un test dédié.

---

## TournamentService

Les tests vérifient notamment :

- création d'un tournoi ;
- fusion des programmes ;
- fusion des sites ;
- enrichissement des données ;
- tri chronologique.

---

## RegistrationService

Les tests vérifient notamment :

- calcul de l'état des inscriptions ;
- gestion des dates d'ouverture ;
- gestion des dates de fermeture.

---

## ParameterService

Les tests vérifient notamment :

- lecture des référentiels ;
- mise en cache des paramètres ;
- comportement en cas de référentiel vide.

---

# Organisation

Les tests suivent la même organisation que les services.

```text
tests/

TournamentServiceTest.gs

ValidationServiceTest.gs

RegistrationServiceTest.gs

ParameterServiceTest.gs
```

Chaque fichier contient exclusivement les tests du service concerné.

---

# Convention de nommage

Les méthodes de test suivent le format :

```javascript
testBuildTournament()

testMergePrograms()

testDuplicateTournamentId()

testRegistrationStatusOpen()
```

Le nom du test décrit toujours le comportement attendu.

---

# Non-régression

Chaque correction d'anomalie devra désormais être accompagnée d'un test reproduisant le problème.

Le cycle est le suivant :

1. reproduire le bug avec un test ;
2. constater l'échec du test ;
3. corriger le code ;
4. vérifier que le test passe.

Cette règle s'applique à toutes les futures évolutions du projet.

---

# Évolutions

La couverture des tests sera enrichie progressivement.

Chaque nouvelle règle métier importante devra être accompagnée :

- d'un scénario de test si nécessaire ;
- d'un ou plusieurs tests automatisés.

La suite de tests devient progressivement la référence de non-régression du projet.

---

# Critères d'acceptation

- Les principaux services disposent d'une première suite de tests.
- Les règles métier critiques sont couvertes.
- Les tests utilisent exclusivement TestKit.
- Tous les tests passent avec succès.
- L'exécution complète est réalisée via `runAllTests()`.
- La structure des fichiers respecte les Coding Guidelines.
