# BC-14.1 — Navigation et persistance des filtres

# Objectif

Cette sous-issue améliore la navigation générale de BadCalendar en réduisant les manipulations répétitives.

L'objectif est que le parent retrouve rapidement les compétitions qui l'intéressent sans avoir à reconfigurer systématiquement les filtres lors de chaque visite.

Cette amélioration repose principalement sur la persistance locale des filtres les plus stables.

---

# Contexte

Les parents consultent BadCalendar régulièrement au cours de la saison.

Certaines préférences évoluent rarement :

- catégorie de l'enfant ;
- portée des compétitions recherchées.

À l'inverse, d'autres filtres varient fréquemment :

- mois ;
- état des inscriptions ;
- type de compétition.

Il n'est donc pas pertinent de mémoriser l'ensemble des filtres.

---

# Principes

La navigation doit respecter les principes suivants :

- limiter les manipulations répétitives ;
- conserver un comportement prévisible ;
- ne jamais masquer d'informations de manière inattendue ;
- rester simple à comprendre.

---

# Persistance des filtres

Seuls les filtres considérés comme permanents sont mémorisés.

Ils sont enregistrés dans le Local Storage du navigateur.

Lors de l'ouverture de l'application, ces valeurs sont automatiquement restaurées.

---

# Filtres persistés

Les filtres suivants sont concernés :

- catégorie ;
- portée.

Ces deux filtres représentent des préférences relativement stables d'un parent.

---

# Filtres non persistés

Les filtres suivants sont volontairement réinitialisés à chaque visite :

- mois ;
- état des inscriptions ;
- type de compétition.

Ils correspondent davantage à une recherche ponctuelle.

---

# Stockage

Les préférences sont stockées exclusivement dans le Local Storage.

Aucune donnée n'est enregistrée côté serveur.

La persistance reste totalement anonyme.

---

# Première visite

Lors de la première ouverture de BadCalendar :

- aucune préférence n'existe ;
- les valeurs par défaut de l'application sont utilisées.

Les préférences sont créées uniquement après la première modification des filtres concernés.

---

# Réinitialisation

Le bouton **Réinitialiser les filtres** conserve son comportement actuel.

Il supprime :

- les filtres actifs ;
- les préférences enregistrées dans le Local Storage.

L'application retrouve alors son comportement initial.

---

# Navigation

La navigation reste basée sur une liste chronologique unique.

Aucune nouvelle vue n'est introduite.

Aucun système d'onglets n'est ajouté.

La simplicité reste une priorité.

---

# Performance

La restauration des préférences doit être instantanée.

Elle ne doit pas augmenter perceptiblement le temps de chargement de l'application.

---

# Architecture

Le frontend est responsable :

- de la lecture du Local Storage ;
- de la restauration des filtres ;
- de leur mise à jour.

Aucune logique métier supplémentaire n'est introduite côté backend.

---

# Hors périmètre

Cette sous-issue ne comprend pas :

- filtres multi-valeurs ;
- badge "Nouveau" ;
- amélioration graphique des cartes ;
- analytics ;
- comptes utilisateurs.

Ces évolutions seront traitées dans des versions ultérieures.

---

# Critères d'acceptation

La sous-issue est considérée terminée lorsque :

- les filtres "Catégorie" et "Portée" sont correctement mémorisés ;
- les autres filtres sont réinitialisés à chaque ouverture ;
- le bouton "Réinitialiser les filtres" supprime également les préférences enregistrées ;
- la navigation reste identique sur desktop et mobile ;
- aucune régression fonctionnelle n'est observée.
