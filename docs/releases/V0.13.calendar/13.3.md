# BC-13.3 — Intégration dans le frontend

# Objectif

Cette sous-issue intègre l'export Google Calendar dans l'interface utilisateur.

L'objectif est de permettre au parent d'ajouter facilement une compétition à son agenda personnel en un clic.

Toute la logique de génération de l'événement est déjà implémentée dans CalendarService.

Le frontend se limite à déclencher cette fonctionnalité.

---

# Contexte

CalendarService est désormais capable de générer une URL Google Calendar complète.

Cette sous-issue consiste à rendre cette fonctionnalité accessible depuis chaque carte de tournoi.

Aucune logique métier supplémentaire n'est introduite.

---

# Parcours utilisateur

Le parcours utilisateur est le suivant.

```
Consultation d'un tournoi

↓

Dépliage de la carte

↓

Clic sur
Ajouter au calendrier

↓

Ouverture de Google Calendar

↓

Validation par l'utilisateur
```

BadCalendar ne crée jamais directement un événement.

La validation finale appartient toujours à Google Calendar.

---

# Emplacement

L'action est disponible uniquement sur une carte dépliée.

Elle est regroupée avec les autres actions du tournoi :

- BadNet
- Google Maps
- Google Calendar

L'objectif est de conserver une interface compacte lorsque les cartes sont repliées.

---

# Libellé

Le bouton utilise un libellé explicite.

Exemple :

```text
Ajouter au calendrier
```

L'utilisateur comprend immédiatement l'action réalisée.

---

# Icône

Le bouton est accompagné d'une icône calendrier.

L'icône améliore la reconnaissance visuelle de l'action.

---

# Ouverture

L'URL générée par CalendarService est ouverte dans un nouvel onglet.

Le comportement est identique aux autres liens externes de l'application.

L'utilisateur conserve ainsi BadCalendar ouvert.

---

# Responsabilités

Le frontend est responsable de :

- afficher le bouton ;
- appeler CalendarService ;
- ouvrir l'URL retournée.

Le frontend ne construit jamais lui-même une URL Google Calendar.

---

# Gestion des erreurs

Si l'URL ne peut pas être générée :

- aucune ouverture n'est réalisée ;
- aucune erreur JavaScript ne doit apparaître ;
- l'application reste pleinement utilisable.

Ce cas reste exceptionnel.

---

# Responsive

Le comportement est identique :

- desktop ;
- tablette ;
- mobile.

Le bouton doit rester facilement accessible sur les petits écrans.

---

# Accessibilité

Le bouton doit être identifiable sans ambiguïté.

L'utilisateur doit comprendre immédiatement qu'il s'agit d'ajouter la compétition dans son calendrier personnel.

---

# Architecture

Le frontend respecte les principes suivants :

- aucune logique métier ;
- aucune construction d'URL ;
- utilisation exclusive de CalendarService.

Toute évolution future concernant Google Calendar devra être réalisée dans le service.

---

# Hors périmètre

Cette sous-issue ne comprend pas :

- analytics ;
- instrumentation ;
- synchronisation Google Calendar ;
- rappels ;
- export ICS ;
- Outlook Calendar.

Ces sujets seront traités dans des versions ultérieures.

---

# Critères d'acceptation

La sous-issue est considérée terminée lorsque :

- un bouton "Ajouter au calendrier" est disponible sur chaque carte dépliée ;
- le bouton utilise CalendarService ;
- Google Calendar s'ouvre correctement ;
- BadCalendar reste ouvert ;
- le comportement est identique sur desktop et mobile ;
- aucune logique Google Calendar n'est présente dans le frontend.
