# BC-13.2 — Assertions

## Objectif

Introduire les assertions de TestKit.

Les assertions constituent le principal point d'interaction entre le développeur et le framework de tests.

Elles permettent d'exprimer simplement le comportement attendu d'un test tout en produisant des messages d'erreur explicites en cas d'échec.

---

# Contexte

La sous-issue BC-13.1 met en place le cœur de TestKit (gestion des suites, exécution et reporting).

Cette sous-issue complète ce socle en fournissant les assertions utilisées dans les tests métier.

---

# Objectifs

À l'issue de cette sous-issue, TestKit doit proposer un ensemble réduit d'assertions couvrant les principaux besoins du projet.

Les assertions doivent être :

- simples ;
- lisibles ;
- déterministes ;
- faciles à maintenir.

---

# Hors périmètre

Cette sous-issue ne comprend pas :

- les premiers tests métier ;
- les jeux de données ;
- les mocks ;
- les spies ;
- les matchers avancés.

---

# Principes

Les assertions doivent respecter les principes suivants :

- une assertion vérifie un seul comportement ;
- un échec produit un message explicite ;
- les assertions ne modifient jamais les données testées ;
- une assertion en échec interrompt immédiatement le test.

---

# API publique

La première version expose uniquement les assertions suivantes :

```javascript
TestKit.assertTrue(value);

TestKit.assertFalse(value);

TestKit.assertEquals(expected, actual);

TestKit.assertNotEquals(expected, actual);

TestKit.assertNull(value);

TestKit.assertNotNull(value);

TestKit.assertThrows(callback);

TestKit.fail(message);
```

Le framework ne fournit volontairement qu'un nombre limité d'assertions.

Toute nouvelle assertion devra répondre à un besoin réel du projet.

---

# Utilisation

Exemple :

```javascript
TestKit
  .suite("TournamentService")

  .test("Tournament title", function () {

    const tournament = ...

    TestKit.assertEquals(
      "TRJ Rennes",
      tournament.title
    );

  });
```

---

# assertEquals()

Vérifie que deux valeurs sont strictement identiques.

Exemple :

```javascript
TestKit.assertEquals(2, programs.length);
```

En cas d'échec :

```text
Expected : 2

Actual   : 3
```

---

# assertTrue()

Vérifie qu'une expression est vraie.

Exemple :

```javascript
TestKit.assertTrue(tournament.isOpen);
```

---

# assertFalse()

Vérifie qu'une expression est fausse.

Exemple :

```javascript
TestKit.assertFalse(tournament.isCancelled);
```

---

# assertNull()

Vérifie qu'une valeur est nulle.

---

# assertNotNull()

Vérifie qu'une valeur est définie.

---

# assertNotEquals()

Vérifie que deux valeurs sont différentes.

---

# assertThrows()

Vérifie qu'une fonction lève une exception.

Exemple :

```javascript
TestKit.assertThrows(function () {

  ValidationService.validate(...);

});
```

---

# fail()

Permet de provoquer volontairement l'échec d'un test.

Exemple :

```javascript
if (!condition) {
  TestKit.fail("Unexpected configuration.");
}
```

---

# Gestion des erreurs

Toutes les assertions produisent une AssertionError.

Cette erreur contient notamment :

- le type d'assertion ;
- la valeur attendue (si applicable) ;
- la valeur obtenue (si applicable) ;
- un message explicatif.

Le TestRunner est responsable de capturer cette erreur.

---

# Messages d'erreur

Les messages doivent être explicites.

Exemple :

```text
Assertion failed

assertEquals()

Expected :
2

Actual :
3
```

L'objectif est de permettre au développeur d'identifier immédiatement la cause de l'échec.

---

# Simplicité

TestKit ne cherche pas à reproduire l'ensemble des fonctionnalités de frameworks comme JUnit ou Jest.

Les assertions restent volontairement limitées afin de conserver :

- une API simple ;
- une implémentation légère ;
- une maintenance minimale.

---

# Critères d'acceptation

- Toutes les assertions sont disponibles via TestKit.
- Chaque assertion produit une AssertionError en cas d'échec.
- Les messages d'erreur sont lisibles.
- Les assertions n'ont aucun effet de bord.
- Les assertions sont documentées.
