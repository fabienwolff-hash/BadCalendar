# BC-13.3 — Test Data

## Objectif

Mettre en place les jeux de données de référence utilisés par les tests automatisés de BadCalendar.

Chaque jeu de données représente un scénario métier précis.

Ils permettent de vérifier de manière reproductible le comportement des services métier et de prévenir les régressions lors des évolutions du projet.

---

# Contexte

Le framework TestKit permet désormais d'exécuter des tests automatisés.

Afin de garantir leur stabilité, les tests doivent s'appuyer sur des données simples, indépendantes et représentatives des principaux cas métier.

Les jeux de données deviennent une référence commune pour l'ensemble des tests.

---

# Objectifs

À l'issue de cette sous-issue :

- une bibliothèque de scénarios de référence est disponible ;
- chaque scénario possède un objectif clairement identifié ;
- les scénarios peuvent être réutilisés par plusieurs tests ;
- les données sont indépendantes des implémentations des services.

---

# Principes

Les jeux de données doivent respecter les principes suivants :

- un scénario = un objectif métier ;
- données minimales ;
- aucune duplication inutile ;
- lecture simple ;
- indépendance entre scénarios.

Un scénario ne doit contenir que les données nécessaires au comportement testé.

---

# Organisation

Les jeux de données sont regroupés dans un répertoire dédié.

```text
tests/

data/

    valid/

    invalid/

    edge-cases/
```

Cette organisation permet de distinguer les scénarios attendus des cas d'erreur et des cas limites.

---

# Catégories de scénarios

## Scénarios valides

Ils représentent des situations conformes aux règles métier.

Exemples :

- tournoi simple ;
- tournoi multi-programmes ;
- tournoi multi-sites ;
- stage ;
- championnat.

Ces scénarios servent principalement aux tests de construction et d'enrichissement des événements.

---

## Scénarios invalides

Ils représentent des erreurs devant être détectées par ValidationService.

Exemples :

- identifiant dupliqué ;
- catégorie inconnue ;
- type invalide ;
- portée invalide ;
- dates incohérentes ;
- programme inexistant.

Chaque scénario correspond à une règle métier.

---

## Cas limites

Ils permettent de vérifier le comportement dans des situations particulières.

Exemples :

- aucun événement ;
- un seul événement ;
- très grand nombre d'événements ;
- valeurs optionnelles absentes ;
- événement avec plusieurs programmes.

---

# Convention de nommage

Les noms doivent décrire le comportement testé.

Exemples :

```text
valid-single-tournament

valid-multi-program

valid-multi-site

invalid-duplicate-id

invalid-category

invalid-registration-dates

empty-master
```

Les noms techniques ou les numéros de version sont à éviter.

---

# Réutilisation

Un même scénario peut être utilisé par plusieurs tests.

Exemple :

```text
valid-multi-program
```

peut être utilisé pour tester :

- TournamentService ;
- ValidationService ;
- RegistrationService.

Le scénario ne doit jamais être modifié pour répondre à un test particulier.

---

# Maintenance

Lorsqu'une nouvelle règle métier est introduite :

- un nouveau scénario est créé si nécessaire ;
- les scénarios existants sont mis à jour uniquement si la règle métier évolue.

Les jeux de données constituent une documentation vivante du domaine métier.

---

# Évolutions

À terme, les scénarios pourront être utilisés pour :

- les tests unitaires ;
- les tests d'intégration ;
- les tests de non-régression.

Ils deviendront la référence unique des données de test du projet.

---

# Critères d'acceptation

- Une structure dédiée aux jeux de données est créée.
- Les principaux scénarios métier sont identifiés.
- Les scénarios sont organisés par catégorie.
- Les conventions de nommage sont définies.
- Les scénarios sont indépendants et réutilisables.
