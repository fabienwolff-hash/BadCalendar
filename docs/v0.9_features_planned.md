# V0.9.md

# BadCalendar — Roadmap détaillée de la version 0.9

## Objectif de la version

La version **0.9** constitue la dernière grande phase d'évolution fonctionnelle avant la stabilisation du projet en **V1.0**.

Après la V0.8, l'architecture est désormais considérée comme stable :

- backend structuré ;
- frontend découpé par responsabilités ;
- modèle de données stabilisé ;
- documentation complète.

La V0.9 se concentre donc principalement sur :

- l'amélioration de l'expérience utilisateur ;
- le confort d'utilisation ;
- la richesse fonctionnelle ;
- les derniers raffinements ergonomiques.

Aucune refonte majeure de l'architecture n'est prévue.

---

# Philosophie de la V0.9

Les évolutions doivent respecter les principes suivants :

- ne jamais casser les fonctionnalités existantes ;
- rester incrémentales ;
- être testables indépendamment ;
- conserver un code simple ;
- préparer la V1.0.

Chaque évolution est découpée en sous-issues courtes.

---

# Epic 12 — Amélioration des filtres

## Objectif

Faire des filtres un véritable outil de recherche confortable.

---

## 12.3 Suppression rapide d'un filtre

Chaque filtre actif devient une puce.

Exemple :

```
[ TDJ × ]

[ Benjamin × ]

[ Novembre × ]
```

Cliquer sur :

```
×
```

supprime uniquement ce filtre.

Sans rouvrir les filtres.

---

## 12.5 Filtres multi-valeurs

Aujourd'hui :

```
TDJ
```

Demain :

```
✓ TDJ

✓ TRJ

✓ TIJ
```

Même principe pour :

- catégories
- portée
- mois

---

Cette évolution représente probablement la plus grosse de la V0.9.

# Epic 13 — Amélioration des cartes

## 13.1 Statut visuel des événements

Exemple :

```

```

vert

```

```

orange

```

```

gris

---

## 13.3 Icônes homogènes

Remplacer progressivement

📍

👦

👥

📝

par un jeu cohérent.

Exemple :

ou

Font Awesome.

Sans dépendance externe si possible.

Aujourd'hui :

```

```


# Critères de sortie de la V0.9

La version sera considérée comme terminée lorsque :

- toutes les sous-issues auront été validées ;
- les tests desktop, tablette et mobile seront concluants ;
- la documentation sera mise à jour ;
- une nouvelle revue de code sera effectuée ;
- la roadmap V1.0 sera définie.

La V0.9 doit constituer une version **quasi finalisée**, ne laissant à la V1.0 que les dernières optimisations, la stabilisation et la préparation à une première diffusion.
