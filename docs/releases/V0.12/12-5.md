# BC-12.5 — Finalisation de la migration et stabilisation

## Version

v0.12

---

# Contexte

Les sous-issues précédentes ont introduit :

- le nouveau modèle métier ;
- TournamentService ;
- la refonte de ValidationService ;
- la migration du frontend.

Le projet fonctionne désormais avec le modèle Tournament.

Cette dernière sous-issue a pour objectif de finaliser la migration, supprimer les éléments devenus obsolètes et stabiliser la version avant la reprise des évolutions fonctionnelles.

---

# Objectif

Finaliser la migration vers le nouveau modèle métier en :

- supprimant le code devenu inutile ;
- harmonisant l'architecture ;
- mettant à jour la documentation ;
- vérifiant l'absence de régressions.

Aucune nouvelle fonctionnalité n'est introduite.

---

- architecture.md
- coding_guidelines.md
- tests.md

- BC-12.1-domain-model.md
- BC-12.2-tournament-service.md
- BC-12.3-validation-service.md
- BC-12.4-frontend-migration.md

---

# Suppression du code obsolète

Supprimer les composants devenus inutiles après la migration.

Exemples :

- ancien modèle Event ;
- méthodes non utilisées ;
- constantes devenues inutiles ;
- fonctions remplacées ;
- commentaires obsolètes.

Le nettoyage doit être limité au périmètre de la migration.

Aucun refactoring supplémentaire n'est réalisé.

---

# Harmonisation de l'architecture

Vérifier que :

- TournamentService est l'unique responsable de la construction du modèle métier ;
- ValidationService est l'unique responsable de la validation ;
- le frontend ne contient aucune logique métier.

Supprimer toute duplication introduite pendant la migration.

---

# Documentation

Mettre à jour la documentation afin qu'elle reflète l'état réel du projet.

Vérifier notamment :

- architecture.md ;
- data_model.md ;
- glossary.md ;
- release_note.md.

Ajouter les décisions importantes dans decisions.md si nécessaire.

---

# Version de l'application

Afficher le numéro de version dans l'écran de chargement.

Le numéro est lu depuis Config.gs.

L'utilisateur peut ainsi identifier facilement la version utilisée.

---

# Tests

Exécuter l'ensemble des tests définis dans tests.md.

Vérifier notamment :

- chargement du calendrier ;
- affichage des cartes ;
- fonctionnement des filtres ;
- ouverture des liens BadNet ;
- ouverture de Google Maps ;
- export Google Calendar ;
- validation du Master.

Aucune régression ne doit être constatée.

---

# Vérification documentaire

Avant clôture de la version :

- documentation synchronisée ;
- roadmap mise à jour ;
- release notes complétées ;
- sous-issues fermées.

---

# Hors périmètre

Cette sous-issue ne comprend pas :

- nouvelles fonctionnalités ;
- amélioration UX ;
- analytics ;
- optimisation des performances ;
- nouveaux filtres.

Ces évolutions appartiennent aux versions suivantes.

---

# Critères d'acceptation

- Le modèle Event n'est plus utilisé.
- Le code obsolète a été supprimé.
- L'architecture est cohérente avec les documents de référence.
- La documentation est à jour.
- Le numéro de version est affiché dans l'application.
- Tous les tests sont passants.
- La release checklist est validée.
