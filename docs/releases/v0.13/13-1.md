# BC-13.1 — TestKit Core

## Objectif

Mettre en place le cœur du framework de tests automatisés de BadCalendar.

Cette sous-issue pose les fondations de TestKit, le framework interne utilisé pour exécuter les tests métier du projet.

L'objectif n'est pas encore d'écrire les premiers tests, mais de fournir une infrastructure simple, stable et réutilisable.

---

# Contexte

BadCalendar s'appuie principalement sur une logique métier implémentée dans le backend Google Apps Script.

Afin de sécuriser les futures évolutions, le projet introduit un framework de tests léger, spécifiquement conçu pour les besoins de BadCalendar.

Le framework doit rester simple, sans dépendance externe et parfaitement adapté à Google Apps Script.

---

# Objectifs

À l'issue de cette sous-issue, il doit être possible de :

- déclarer une suite de tests ;
- enregistrer automatiquement cette suite ;
- déclarer plusieurs tests au sein d'une suite ;
- exécuter toutes les suites via un point d'entrée unique ;
- afficher un rapport d'exécution lisible.

Aucun test métier n'est encore implémenté.

---

# Hors périmètre

Cette sous-issue ne comprend pas :

- les assertions ;
- les jeux de données ;
- les tests métier ;
- les mocks ;
- les tests frontend.

Ces éléments seront traités dans les sous-issues suivantes.

---

# Principes

TestKit respecte les principes suivants :

- simplicité avant richesse fonctionnelle ;
- aucune dépendance externe ;
- API minimale ;
- découverte automatique des suites ;
- architecture modulaire ;
- exécution déterministe.

Le framework est développé exclusivement pour BadCalendar.

---

# API publique

La première version expose uniquement les méthodes suivantes :

```javascript
TestKit.suite(name)

TestKit.run()

TestKit.run(suiteName)
```

Le développeur ne manipule aucune autre classe.

---

# Déclaration d'une suite

Une suite représente un regroupement logique de tests.

Exemple :

```javascript
TestKit
  .suite("TournamentService")
  .test("Build Tournament", function () {

    // ...

  })
  .test("Merge Programs", function () {

    // ...

  });
```

La déclaration d'une suite provoque automatiquement son enregistrement.

Aucune configuration supplémentaire n'est nécessaire.

---

# Exécution

L'ensemble des tests est lancé via :

```javascript
runAllTests();
```

Cette fonction délègue l'exécution à :

```javascript
TestKit.run();
```

Il est également possible d'exécuter une seule suite :

```javascript
TestKit.run("TournamentService");
```

---

# Architecture

Le framework est organisé autour des composants suivants :

```text
TestKit
│
├── TestRegistry
├── TestSuite
├── TestRunner
└── TestReporter
```

Chaque composant possède une responsabilité unique.

---

## TestRegistry

Responsable de l'enregistrement des suites.

Il constitue la mémoire du framework.

---

## TestSuite

Représente une suite de tests.

Elle contient :

- un nom ;
- une liste de tests.

Chaque test est composé :

- d'un nom ;
- d'une fonction.

---

## TestRunner

Responsable de l'exécution des suites.

Il ne réalise aucun affichage.

Il collecte uniquement les résultats.

---

## TestReporter

Responsable de l'affichage des résultats.

Il ne connaît pas le fonctionnement interne des tests.

---

# Rapport attendu

L'exécution produit un résumé de la forme :

```text
=========================================
BadCalendar TestKit

TournamentService

  ✔ Build Tournament
  ✔ Merge Programs

ValidationService

  ✔ Duplicate Tournament

-----------------------------------------

Suites : 2

Tests  : 3

Passed : 3

Failed : 0

Duration : 31 ms

=========================================
```

Le rapport doit rester lisible dans les journaux Google Apps Script.

# Critères d'acceptation

- TestKit expose une API publique simple.
- Une suite s'enregistre automatiquement.
- Plusieurs suites peuvent coexister.
- Le runner découvre toutes les suites.
- L'exécution ne nécessite aucune configuration.
- Un rapport synthétique est affiché.
- Le code respecte les Coding Guidelines du projet.
