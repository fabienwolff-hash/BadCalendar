# BC-13.1 — CalendarService

# Objectif

Cette sous-issue met en place le service responsable de la génération des liens Google Calendar.

L'objectif est d'isoler toute la logique de construction de l'événement dans un composant unique afin de conserver un frontend simple et une architecture cohérente.

À l'issue de cette sous-issue, aucun composant frontend ne construit directement une URL Google Calendar.

---

# Contexte

La version v0.13 introduit l'export d'une compétition vers Google Calendar.

Cette fonctionnalité permet au parent d'ajouter facilement une compétition dans son agenda personnel.

L'application ne crée jamais directement un événement dans Google Calendar.

Elle génère simplement une URL préremplie qui est ouverte dans un nouvel onglet.

Google Calendar reste responsable de la création définitive de l'événement.

---

# Principe

Toute la logique de génération est centralisée dans un unique service.

```text
Tournament
        │
        ▼
CalendarService
        │
        ▼
Google Calendar URL
```

Le frontend n'a pas connaissance du format attendu par Google Calendar.

Il demande simplement au service de générer l'URL.

---

# Responsabilités

CalendarService est responsable de :

- construire le titre de l'événement ;
- construire la période de l'événement ;
- construire le lieu ;
- construire la description ;
- encoder correctement les paramètres de l'URL ;
- retourner une URL valide.

Le service ne réalise aucune ouverture de fenêtre.

---

# API

Le service expose une méthode unique.

```javascript
CalendarService.buildGoogleCalendarUrl(tournament)
```

Entrée :

```text
Tournament
```

Sortie :

```text
String
```

correspondant à l'URL Google Calendar.

---

# Source des données

Toutes les informations proviennent exclusivement du modèle Tournament.

Le service ne réalise aucune lecture directe :

- du Master ;
- des DTO ;
- du frontend.

Tournament constitue la source unique de vérité.

---

# Données utilisées

Le service exploite notamment :

- nom du tournoi ;
- date de début ;
- date de fin ;
- lieu principal ;
- adresse ;
- ville ;
- lien BadNet ;
- lien Google Maps lorsque disponible.

Aucune autre information métier n'est nécessaire.

---

# Gestion des valeurs absentes

Le service doit être tolérant aux données incomplètes.

Exemples :

- aucune adresse connue ;
- aucun lien Google Maps ;
- aucun lieu principal.

Les informations absentes sont simplement ignorées.

Aucune erreur ne doit être générée.

---

# Construction de la description

La description est générée automatiquement.

Elle contient uniquement les informations utiles.

Exemple :

```text
Compétition de badminton

Lieu

Gymnase de la Chesnaie
12 rue des Sports
44000 Nantes

BadNet

https://...

Google Maps

https://...

Ajouté depuis BadCalendar
```

Le format exact reste défini par le service.

Le frontend ne construit jamais cette description.

---

# Encodage

CalendarService est responsable de l'encodage des paramètres de l'URL.

Le frontend ne réalise aucun traitement supplémentaire.

---

# Architecture

Le service respecte les principes suivants :

- KISS ;
- Single Responsibility ;
- Single Source of Truth.

Toute évolution future concernant Google Calendar devra être réalisée dans ce service.

---

# Évolutions futures

Cette architecture permettra ultérieurement d'ajouter :

- export ICS ;
- Outlook Calendar ;
- Apple Calendar.

Sans modifier le frontend.

---

# Hors périmètre

Cette sous-issue ne comprend pas :

- bouton dans l'interface ;
- ouverture du navigateur ;
- analytics ;
- tests fonctionnels ;
- validation UX.

Ces sujets seront traités dans les sous-issues suivantes.

---

# Critères d'acceptation

- CalendarService est créé ;
- une méthode publique permet de générer une URL Google Calendar ;
- le service dépend uniquement du modèle Tournament ;
- aucune logique Google Calendar n'est présente dans le frontend ;
- les données absentes sont correctement gérées ;
- la documentation est mise à jour.
