# BC-12.1 — Implémentation du nouveau modèle métier

## Version

v0.12

---

# Contexte

Jusqu'à présent, BadCalendar repose sur un modèle centré sur la notion d'Event.

Ce modèle est suffisant pour représenter des compétitions simples, mais montre rapidement ses limites lorsque :

- un tournoi comporte plusieurs disciplines ;
- un tournoi se déroule sur plusieurs journées ;
- un tournoi utilise plusieurs gymnases ;
- plusieurs lignes du Master représentent en réalité un même tournoi.

Le modèle actuel oblige à dupliquer des informations communes et ne reflète pas fidèlement le métier.

Afin de préparer les évolutions futures, BadCalendar adopte désormais un modèle centré sur la notion de Tournament.

---

# Objectif

Remplacer le modèle logique "Event" par le modèle métier :

Tournament

↓

Program

↓

Site

sans modifier le comportement visible de l'application.

Cette évolution constitue la nouvelle fondation de l'ensemble du backend.

# Décisions de conception

## Entité Tournament

Le Tournament représente une compétition ou un événement identifié par un TournamentId.

Toutes les informations communes sont portées par cette entité.

Exemples :

- titre
- type
- portée
- organisateur
- inscription
- dates d'inscription
- URL

---

## Entité Program

Un Tournament contient un ou plusieurs Programs.

Chaque Program représente un programme sportif homogène.

Exemples :

- Simple
- Double
- Mixte

Chaque Program possède ses propres caractéristiques :

- disciplines
- dates
- sites

---

## Entité Site

Un Program possède un ou plusieurs Sites.

Un Site représente un lieu physique.

Il est composé de :

- ville
- gymnase (optionnel)

Lorsque le Program ne possède qu'un seul Site, seule la ville est affichée dans l'interface.

---

# Modèle cible

```text
Tournament

├── TournamentId

├── title

├── type

├── scope

├── registration

├── programs[]

│     ├── disciplines[]

│     ├── dates[]

│     └── sites[]

│            ├── city

│            └── gymnasium
```

---

# Impact sur le Master

Aucune nouvelle colonne.

Le Master contient déjà :

- TournamentId
- discipline
- ville
- gymnase
- dates

Le changement concerne uniquement l'interprétation des lignes.

---

# Impact Backend

Cette sous-issue introduit uniquement le modèle métier.

Elle ne modifie pas encore les services.

Le code existant continue de fonctionner.

Les nouveaux objets métier sont créés.

---

# Nouveaux objets

Création des objets :

- Tournament
- Program
- Site
- Registration

Ces objets sont de simples modèles de données.

Ils ne contiennent aucune logique métier.

---

# Impact Frontend

Aucun.

Le frontend continue de recevoir le DTO actuel.

Cette sous-issue ne modifie aucune interface.

---

# Compatibilité

Cette évolution doit être entièrement rétrocompatible.

Aucun comportement utilisateur ne doit changer.

L'objectif est uniquement de préparer les évolutions des sous-issues suivantes.

---

# Tests

Vérifier que :

- les nouveaux objets peuvent être instanciés ;
- le modèle représente tous les cas métier connus ;
- aucune régression n'apparaît dans le fonctionnement actuel.

---

# Hors périmètre

Cette sous-issue ne comprend pas :

- TournamentService
- Validation V2
- adaptation du frontend
- optimisation des performances

Ces éléments seront développés dans les sous-issues suivantes.

---

# Critères d'acceptation

- le modèle Tournament → Program → Site est implémenté ;
- les objets sont documentés ;
- aucune régression fonctionnelle ;
- le code respecte les Coding Guidelines ;
- la documentation est mise à jour.

---

# Dépendances

Aucune.

Cette sous-issue est la première de la version v0.12.

Toutes les autres sous-issues de la version dépendront de ce nouveau modèle métier.
