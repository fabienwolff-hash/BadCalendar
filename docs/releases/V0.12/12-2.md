# BC-12.2 — Implémentation de TournamentService

## Version

v0.12

---

# Contexte

Le modèle métier de BadCalendar repose désormais sur les entités :

- Tournament
- Program
- Site
- Registration

Le rôle de TournamentService est de construire ce modèle à partir des lignes du Master.

Il devient le cœur du backend.

Toutes les autres fonctionnalités (validation, frontend, analytics…) s'appuient sur les objets produits par ce service.

---

# Objectif

Construire une liste de `Tournament` à partir des lignes du Master.

Le service est responsable de :

- regrouper les lignes appartenant à un même tournoi ;
- construire les objets métier ;
- dédupliquer les informations ;
- calculer les propriétés métier ;
- retourner un modèle prêt à être consommé.

# Responsabilité

TournamentService est l'unique service responsable de la construction du modèle métier.

Aucun autre service ne crée de Tournament.

Les autres services consomment uniquement les objets produits.

---

# Entrée

Le service reçoit les lignes du Master.

Chaque ligne représente un programme de compétition.

Le Master est supposé valide.

TournamentService ne réalise aucune validation métier.

---

# Sortie

Le service retourne :

```text
Tournament[]
```

Chaque Tournament est entièrement construit.

Le frontend ne manipule jamais directement les lignes du Master.

---

# Architecture retenue

Architecture volontairement simple.

```
Master

↓

TournamentService

↓

Tournament[]
```

Aucun Repository.

Aucun Builder.

Aucune Factory.

Aucun DTO intermédiaire.

Le service construit directement les objets métier.

---

# Algorithme

TournamentService applique les étapes suivantes.

## Étape 1 — Lecture

Lecture de toutes les lignes du Master.

Les lignes sont conservées dans leur ordre initial.

---

## Étape 2 — Regroupement

Les lignes sont regroupées par TournamentId.

Chaque groupe représente un Tournament.

Exemple :

```
TournamentId = T001

Ligne 1

Ligne 2

Ligne 3
```

↓

```
Tournament T001
```

---

## Étape 3 — Construction du Tournament

Pour chaque groupe :

création d'un Tournament.

Les propriétés communes sont initialisées une seule fois.

Exemples :

- titre
- type
- portée
- organisateur
- URL
- dates d'inscription
- mode d'inscription

Toutes les lignes d'un même Tournament sont supposées cohérentes.

Cette cohérence est garantie par ValidationService.

---

## Étape 4 — Construction des Programs

Chaque ligne produit un Program.

Le Program contient notamment :

- disciplines
- date
- catégories
- Site(s)

Les Programs sont rattachés au Tournament.

---

## Étape 5 — Construction des Sites

Chaque Program construit sa liste de Sites.

Un Site est défini par :

- ville
- gymnase (optionnel)

Deux Sites identiques ne sont créés qu'une seule fois.

La déduplication est automatique.

---

## Étape 6 — Calcul des propriétés métier

Une fois tous les objets construits, TournamentService calcule :

- RegistrationStatus
- TournamentStatus
- textes d'affichage
- badges
- propriétés calculées nécessaires au frontend

Le frontend ne doit recalculer aucune règle métier.

---

## Étape 7 — Tri

Les Programs sont triés chronologiquement.

Les Sites sont triés chronologiquement lorsque plusieurs journées existent.

L'ordre du Master n'est jamais utilisé comme ordre d'affichage.

---

## Étape 8 — Retour

Retour de :

```
Tournament[]
```

entièrement construit.

---

# Déduplication

Les règles suivantes sont appliquées.

## Tournament

Un Tournament est unique par TournamentId.

---

## Program

Chaque ligne produit un Program.

Aucune fusion n'est réalisée.

---

## Site

Deux Sites identiques :

- même ville
- même gymnase

↓

produisent un unique Site.

---

# Calculs métier

TournamentService est responsable de tous les calculs métier.

Exemples :

- statut des inscriptions
- statut du tournoi
- badges
- libellés
- propriétés calculées

Le frontend ne réalise aucun calcul métier.

---

# Validation

TournamentService considère que les données sont déjà valides.

Les incohérences ne sont pas gérées.

Elles doivent être détectées auparavant par ValidationService.

Exemples :

- TournamentId incohérent
- titre différent
- portée différente
- URL différente

Ces cas ne doivent jamais arriver.

---

# Gestion des erreurs

Aucune logique spécifique.

Le service suppose un Master valide.

---

# Impact sur le frontend

Le frontend reçoit toujours une liste de Tournament.

Il n'a plus connaissance du découpage en lignes du Master.

Le frontend consomme uniquement le modèle métier.

---

# Impact sur ValidationService

Aucun impact direct.

ValidationService reste exécuté avant TournamentService.

---

# Performances

La lisibilité prime sur l'optimisation.

Le service réalise :

- une lecture complète ;
- un regroupement ;
- une construction.

Toute optimisation devra être motivée par une mesure.

---

# Tests

Les tests doivent vérifier notamment :

- regroupement correct par TournamentId ;
- création des Tournament ;
- création des Programs ;
- déduplication des Sites ;
- tri chronologique des Programs ;
- tri chronologique des Sites ;
- calcul de RegistrationStatus ;
- calcul de TournamentStatus.

---

# Hors périmètre

Cette sous-issue ne comprend pas :

- ValidationService V2 ;
- migration du frontend ;
- analytics ;
- optimisation des performances.

---

# Critères d'acceptation

- TournamentService est l'unique constructeur du modèle métier.
- Les Tournament sont correctement regroupés par TournamentId.
- Les Programs sont créés.
- Les Sites sont dédupliqués.
- Les propriétés métier sont calculées.
- Le frontend ne contient aucune logique métier.
- Les tests sont passants.
- La documentation est mise à jour.
