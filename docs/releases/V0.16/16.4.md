# BC-16.4 — Finalisation et stabilisation

# Objectif

Cette sous-issue finalise la version v0.16.

Elle consiste à valider le bon fonctionnement du système de collecte des métriques, du tableau de bord Google Sheets et de la documentation avant le lancement de la phase pilote.

Aucune nouvelle fonctionnalité n'est développée dans cette sous-issue.

---

# Contexte

Les sous-issues précédentes ont permis :

- la définition du modèle de collecte ;
- l'instrumentation des principales fonctionnalités ;
- la création du tableau de bord d'analyse.

Cette dernière étape garantit que l'ensemble du dispositif fonctionne de manière fiable et transparente.

---

# Vérifications fonctionnelles

Les scénarios suivants doivent être validés.

## Ouverture de l'application

Vérifier qu'une nouvelle session :

- génère un événement `app_open` ;
- crée une nouvelle SessionId ;
- renseigne correctement la version de l'application.

---

## Utilisation des filtres

Vérifier que :

- chaque modification de filtre génère un événement ;
- les catégories, types, portées, mois et états sont correctement enregistrés ;
- les réinitialisations sont correctement tracées.

---

## Consultation des compétitions

Vérifier que :

- l'ouverture d'une carte génère un événement unique ;
- aucun doublon n'est enregistré.

---

## Actions utilisateur

Vérifier que :

- l'ouverture de BadNet est enregistrée ;
- l'ouverture de Google Maps est enregistrée ;
- l'export Google Calendar est enregistré.

Chaque action doit produire un unique événement.

---

## Dashboard

Vérifier que :

- tous les événements apparaissent dans l'onglet Logs ;
- tous les indicateurs du Dashboard sont correctement mis à jour ;
- les graphiques reflètent les nouvelles données.

Aucune intervention manuelle ne doit être nécessaire.

---

# Robustesse

Vérifier notamment que :

- une erreur de tracking n'interrompt jamais l'application ;
- aucune erreur JavaScript n'est générée ;
- les événements restent correctement enregistrés après plusieurs sessions.

---

# Performance

Vérifier que :

- le tracking n'introduit aucun ralentissement perceptible ;
- les actions utilisateur restent instantanées ;
- le Dashboard reste réactif avec un volume important de données.

---

# Documentation

Mettre à jour si nécessaire :

- usage_metrics.md ;
- dashboard.md ;
- architecture.md ;
- release_note.md ;
- release_checklist.md.

La documentation doit refléter fidèlement le fonctionnement du système de collecte.

---

# Release Checklist

Avant de clôturer la sous-issue, vérifier notamment que :

- les critères d'acceptation des BC-16.1 à BC-16.3 sont validés ;
- les événements sont correctement enregistrés ;
- les indicateurs sont cohérents ;
- le Dashboard est entièrement automatisé ;
- aucune anomalie bloquante n'est identifiée ;
- la documentation est synchronisée.

---

# Hors périmètre

Cette sous-issue ne comprend pas :

- nouvelles métriques ;
- nouveaux tableaux de bord ;
- recommandations automatiques ;
- intégration d'outils d'analyse externes.

Ces évolutions pourront être étudiées après la v1.0.

---

# Critères d'acceptation

La sous-issue est considérée terminée lorsque :

- tous les événements sont correctement enregistrés ;
- le Dashboard est alimenté automatiquement ;
- les indicateurs sont cohérents avec les données de l'onglet Logs ;
- aucune anomalie bloquante n'est observée ;
- la documentation est synchronisée ;
- la Release Checklist est validée.

La version v0.16 peut alors être clôturée.

---

# Livrable attendu

À l'issue de cette sous-issue :

- BadCalendar dispose d'un système complet de métriques d'utilisation ;
- les données collectées sont fiables, anonymes et exploitables ;
- le Dashboard permet de suivre l'adoption de l'application pendant le pilote ;
- la documentation est à jour ;
- la version v0.16 est prête à être livrée.
