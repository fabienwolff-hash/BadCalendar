# BC-15.1 — Nouveau modèle de filtres

# Objectif

Cette sous-issue fait évoluer le modèle de filtrage de BadCalendar afin de permettre la sélection de plusieurs valeurs pour un même critère.

Elle constitue la fondation technique des filtres avancés introduits dans la version v0.15.

Aucune évolution visuelle n'est réalisée dans cette sous-issue.

---

# Contexte

Le modèle actuel considère qu'un filtre possède une unique valeur.

Exemple :

```text
Catégorie = Minime
```

Cette représentation devient insuffisante lorsqu'un parent souhaite consulter plusieurs catégories simultanément.

Le modèle doit désormais accepter plusieurs valeurs par filtre.

---

# Nouveau principe

Chaque filtre est représenté par une collection de valeurs sélectionnées.

Exemple :

```text
Catégorie

✓ Minime
✓ Cadet
✓ Junior
```

Le filtre est satisfait lorsqu'un tournoi correspond à au moins une valeur sélectionnée.

---

# Filtres concernés

Les filtres suivants deviennent multi-valeurs :

- Catégorie
- Type
- Portée
- État des inscriptions

Le filtre Mois conserve son fonctionnement actuel.

---

# Comportement

Lorsqu'aucune valeur n'est sélectionnée :

- le filtre est considéré comme inactif ;
- aucune restriction n'est appliquée.

Le comportement reste identique à la version précédente.

---

# Règle de filtrage

Pour chaque filtre :

- un tournoi est conservé s'il correspond à au moins une valeur sélectionnée ;
- plusieurs filtres restent combinés par un opérateur logique **ET**.

Exemple :

```text
Catégorie

Cadet
OU
Junior

ET

Portée

Départementale
OU
Régionale
```

---

# Représentation interne

Chaque filtre manipule désormais une liste de valeurs.

Exemple :

```javascript
categories = [
    "Cadet",
    "Junior"
]
```

Plutôt qu'une unique chaîne de caractères.

---

# Compatibilité

Le nouveau modèle doit rester compatible avec :

- la persistance locale ;
- les filtres existants ;
- le backend.

Aucune régression fonctionnelle ne doit être introduite.

---

# Architecture

Le modèle de filtre devient la référence unique utilisée par :

- le frontend ;
- la persistance des préférences ;
- le moteur de filtrage.

Toutes les couches utilisent la même représentation.

---

# Performance

Le nouveau modèle ne doit pas entraîner de ralentissement perceptible.

Le nombre de compétitions restant limité, aucune optimisation spécifique n'est nécessaire.

La simplicité est privilégiée.

---

# Évolutivité

Le modèle doit permettre d'ajouter facilement de nouveaux filtres multi-valeurs dans les versions futures.

Aucune hypothèse ne doit être faite sur le nombre maximal de valeurs sélectionnées.

---

# Hors périmètre

Cette sous-issue ne comprend pas :

- nouvelle interface utilisateur ;
- cases à cocher ;
- analytics ;
- persistance des nouveaux formats ;
- optimisation graphique.

Ces sujets seront traités dans les sous-issues suivantes.

---

# Critères d'acceptation

La sous-issue est considérée terminée lorsque :

- les filtres concernés utilisent une collection de valeurs ;
- le comportement des filtres inactifs reste inchangé ;
- la logique ET/OU est correctement définie ;
- le modèle est compatible avec les autres composants ;
- aucune régression fonctionnelle n'est observée.
